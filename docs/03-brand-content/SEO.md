## 1. Purpose & Scope

### 1.1. Цель документа

Определить стратегию поисковой оптимизации и органического привлечения клиентов для строительной компании «Братья» на рынках Армении и международной аудитории.

SEO-стратегия должна обеспечивать:

- Органическую видимость сайта в поисковых системах.
- Привлечение потенциальных клиентов по коммерческим запросам.
- Продвижение отдельных строительных услуг.
- Индексацию проектов и портфолио.
- Привлечение армянской диаспоры.
- Повышение доверия к компании через экспертный контент.
- Подготовку сайта к поиску с использованием AI-систем.

### 1.2. Основные направления

1. Technical SEO.
2. On-Page SEO.
3. Local SEO.
4. International SEO.
5. Content SEO.
6. Image & Video SEO.
7. Structured Data.
8. GEO — Generative Engine Optimization.
9. SEO Analytics & Monitoring.

### 1.3. Основной принцип

Продвижение должно строиться вокруг реальных услуг, реальных объектов и подтверждённой компетентности компании.

Не использовать:

- Массовую генерацию однотипных SEO-страниц.
- Искусственное насыщение текстов ключевыми словами.
- Вымышленные отзывы и рейтинги.
- Неподтверждённые заявления о количестве объектов и опыте.
- Публикацию несуществующих адресов и филиалов.
- Покупку некачественных ссылок.

## 2. SEO Goals & KPIs

### 2.1. Business Goals

Основная цель — получение квалифицированных обращений от клиентов, заинтересованных в строительстве, ремонте и реализации архитектурных проектов в Армении.

Приоритетные конверсии:

- WhatsApp Click.
- Telegram Click.
- Phone Click.
- Email Click.
- Lead Form Submission.
- Qualified Lead.

Важно различать обычное взаимодействие с сайтом и реальную заявку. Клик по WhatsApp не является подтверждённым лидом до получения обращения.

### 2.2. SEO KPIs

#### Visibility

- Organic Impressions.
- Organic Clicks.
- Search Queries.
- Average Position.
- Indexed Pages.

#### Engagement

- Organic Landing Page Sessions.
- Engaged Sessions.
- Service Page Engagement.
- Project Page Engagement.

#### Conversion

- Leads from Organic Search.
- Qualified Leads from Organic Search.
- Conversion Rate.
- Cost per Lead — при наличии рекламных расходов.

#### Technical

- Core Web Vitals.
- Crawl Errors.
- Indexing Errors.
- Broken Links.
- Duplicate Metadata.
- Structured Data Validation.

### 2.3. Целевые технические показатели

Внутренние цели проекта:

- LCP ≤ 2.5 seconds.
- INP ≤ 200 ms.
- CLS ≤ 0.1.
- Lighthouse Performance ≥ 90.
- Lighthouse SEO ≥ 95.
- Lighthouse Accessibility ≥ 90.
- Lighthouse Best Practices ≥ 95.

Core Web Vitals оцениваются по реальным пользовательским данным, а не только по лабораторному Lighthouse-тесту.

Эти показатели являются целями качества, а не гарантией поискового ранжирования.

## 5. Website SEO Architecture

### 5.1. URL Structure

Основной формат:

`/{locale}/{section}/{slug}/`

Примеры:

```text
/hy/
/ru/
/en/

/hy/services/
/ru/services/
/en/services/

/hy/projects/
/ru/projects/
/en/projects/

/hy/services/private-houses/
/ru/services/stroitelstvo-chastnyh-domov/
/en/services/private-house-construction/
```

Рекомендации:

- Использовать понятные URL.
- Избегать случайных идентификаторов.
- Не менять опубликованные URL без необходимости.
- При изменении URL настраивать 301 Redirect.
- Не использовать query parameters для языковых версий.
- Каждая индексируемая страница должна иметь собственный canonical.

### 5.2. International SEO

Для каждой опубликованной локализованной страницы необходимо:

- Указать правильный язык HTML через `lang`.
- Указать canonical на соответствующую языковую версию.
- Добавить взаимные `hreflang`-ссылки.
- Обеспечить корректное переключение языка.
- Включать только существующие переводы.
- Не создавать фиктивные языковые страницы.

Пример:

```html
<link
  rel="alternate"
  hreflang="hy"
  href="https://example.am/hy/services/example/"
/>

<link
  rel="alternate"
  hreflang="ru"
  href="https://example.am/ru/services/example/"
/>

<link
  rel="alternate"
  hreflang="en"
  href="https://example.am/en/services/example/"
/>
```

При необходимости можно добавить `x-default`, указывающий на нейтральную языковую страницу или языковой selector.

`hreflang` должен быть взаимным: каждая версия ссылается на остальные доступные версии, включая себя.

### 5.3. Canonical Strategy

- Каждая индексируемая страница имеет self-referencing canonical.
- Переводы не должны указывать canonical на другую языковую версию.
- Дублирующиеся URL должны консолидироваться.
- Параметры сортировки и фильтрации не должны создавать индексируемые дубли.
- Canonical должен совпадать с URL, включённым в sitemap.

### 5.4. Sitemap

Рекомендуется автоматически генерировать XML Sitemap из опубликованного контента Astro.

Включать:

- Homepage.
- Services.
- Projects.
- Articles.
- About.
- Contact.
- Другие опубликованные страницы, предназначенные для индексации.

Не включать:

- Draft.
- Archived.
- Страницы с `noindex`.
- Несуществующие переводы.
- Redirect URLs.
- Дублирующиеся URL.

Для мультиязычных страниц sitemap должен поддерживать соответствующие alternate language annotations.

Предлагаемый endpoint:

`/sitemap-index.xml`

### 5.5. Robots.txt

Рекомендуемый путь:

`/robots.txt`

Требования:

- Разрешить обход публичного контента.
- Указать sitemap.
- Не блокировать CSS и JS, необходимые для рендеринга.
- Исключить служебные и приватные маршруты при необходимости.
- Не использовать robots.txt как замену canonical или noindex.

Пример:

```text
User-agent: *
Allow: /

Sitemap: https://example.am/sitemap-index.xml
```

Окончательный файл будет зависеть от реальных маршрутов приложения.

## 6. On-Page SEO

### 6.1. Page Metadata

Каждая индексируемая страница должна иметь:

- SEO Title.
- Meta Description.
- Canonical URL.
- H1.
- Open Graph Title.
- Open Graph Description.
- Open Graph Image.
- Locale.
- Robots Directive.

### 6.2. Title Guidelines

- Уникальный для каждой страницы.
- Описывает фактическое содержание.
- Содержит основной поисковый интент.
- При необходимости содержит географию.
- Не перегружен ключевыми словами.
- Не дублирует механически заголовки других страниц.

Пример:

`Строительство частных домов в Армении | Братья`

### 6.3. Meta Description

Описание должно:

- Кратко раскрывать содержание страницы.
- Объяснять ценность услуги.
- Содержать естественную формулировку.
- Соответствовать языку страницы.
- Не содержать неподтверждённых обещаний.

Пример:

`Строительство частных домов в Армении. Обсудите проект, этапы реализации и возможный состав работ с командой «Братья».`

Поисковая система может сформировать сниппет самостоятельно, поэтому meta description не гарантирует отображение именно заданного текста.

### 6.4. Heading Structure

- Один основной H1.
- H2 для основных разделов.
- H3 для подразделов.
- Логическая иерархия заголовков.
- Не использовать заголовки только ради визуального размера.

### 6.5. Internal Linking

Каждая страница должна иметь логические связи с другими материалами.

Примеры:

Service → Related Projects.

Project → Related Services.

Article → Relevant Services.

Article → Relevant Projects.

Homepage → Featured Services.

Homepage → Selected Projects.

Цель — упростить навигацию пользователей и обнаружение связанных страниц поисковыми системами.

## 7. Local SEO

### 7.1. География продвижения

Основной регион:

- Yerevan.

Дополнительная география:

- Другие регионы Армении.

Необходимо подтвердить фактические территории, в которых компания принимает и выполняет заказы.

### 7.2. Google Business Profile

Если компания соответствует требованиям Google Business Profile, необходимо создать и подтвердить профиль.

Заполняемые сведения:

- Реальное название компании.
- Основная категория бизнеса.
- Дополнительные категории, если применимо.
- Реальные контактные данные.
- Веб-сайт.
- Часы работы.
- Адрес или корректная service area configuration.
- Фотографии объектов.
- Описание деятельности.

Если компания обслуживает клиентов на выезде и не принимает посетителей по адресу, необходимо корректно настроить профиль как service-area business в соответствии с правилами Google.

Не использовать фиктивные офисы или адреса.

### 7.3. NAP Consistency

NAP означает:

- Name.
- Address.
- Phone.

Название, адрес и телефон должны быть согласованы между сайтом, Google Business Profile и другими официальными площадками.

Если публичного офиса нет, не публиковать вымышленный адрес ради локального SEO.

### 7.4. Local Landing Pages

Локальные страницы создавать только при наличии реального содержания.

Пример возможной структуры:

- Construction in Yerevan.
- Renovation in Yerevan.
- Construction Services in Armenia.

Дополнительные региональные страницы создавать только при наличии:

- Реальных выполненных объектов.
- Подтверждённого обслуживания территории.
- Уникальной информации.
- Полезного контента для локального пользователя.

Не создавать десятки одинаковых страниц с заменой названия города.

### 7.5. Reviews

Отзывы:

- Должны быть реальными.
- Должны принадлежать действительным заказчикам.
- Должны публиковаться с разрешения.
- Не должны редактироваться с изменением смысла.
- Не должны генерироваться искусственно.

## 9. Image & Video SEO

### 9.1. Image Optimization

Каждое важное изображение должно:

- Иметь осмысленное имя файла.
- Иметь корректный alt.
- Иметь подходящий формат.
- Быть оптимизировано по размеру.
- Иметь заданные размеры или aspect ratio.
- Находиться рядом с релевантным текстом.

Пример:

`private-house-yerevan-exterior.webp`

Не использовать бессмысленные названия:

`IMG_00123.jpg`

### 9.2. Alt Text

Alt должен описывать изображение, а не повторять ключевые слова.

Пример:

`Современный фасад частного дома с панорамными окнами`

Для декоративных изображений использовать пустой alt, если изображение не передаёт самостоятельную информацию.

### 9.3. Image Formats

Рекомендуемые форматы:

- AVIF.
- WebP.
- JPEG — при необходимости совместимости или для исходных материалов.

Использовать responsive image delivery и оптимальные размеры.

### 9.4. Video SEO

Для видео:

- Уникальный заголовок.
- Описание.
- Превью.
- Текстовый контекст на странице.
- При необходимости субтитры.
- Корректные метаданные.

Если видео размещено на YouTube, необходимо связать его с соответствующим проектом или услугой.

Не рассчитывать на SEO только за счёт видео без содержательного текстового сопровождения.

## 10. Structured Data

### 10.1. Общий принцип

Использовать JSON-LD для описания сущностей и содержания сайта.

Разметка должна соответствовать информации, видимой пользователю.

### 10.2. Recommended Schema Types

**Organization**

Для описания компании:

- name.
- alternateName.
- url.
- logo.
- image.
- telephone.
- email.
- address — если применимо.
- sameAs — только реальные официальные профили.

**LocalBusiness**

Рассматривать при наличии соответствующего физического или локального присутствия и данных, необходимых для выбранного типа разметки.

Не указывать вымышленный адрес.

**Service**

Для описания конкретных строительных услуг.

**Article**

Для экспертных материалов.

**BreadcrumbList**

Для навигационной структуры страниц.

**ImageObject**

Для значимых изображений, если это оправдано структурой данных.

### 10.3. Reviews & Ratings

Не создавать фиктивную AggregateRating-разметку.

Не размечать собственные отзывы компании так, будто они являются независимыми отзывами сторонних организаций.

Разметка должна соответствовать актуальным требованиям поисковой системы.

### 10.4. Validation

Проверять:

- Schema Markup Validator.
- Google Rich Results Test.
- Google Search Console.

Наличие корректной разметки не гарантирует отображение расширенного результата.

## 11. GEO — Generative Engine Optimization

### 11.1. Цель GEO

Повысить вероятность того, что материалы компании будут обнаруживаться, пониматься и использоваться поисковыми и генеративными AI-системами в качестве источника информации.

Речь идёт о поисковых сценариях, в которых пользователь задаёт вопрос естественным языком и получает сформированный ответ с источниками.

### 11.2. Основные принципы

**1. Entity Clarity**

Сайт должен последовательно описывать:

- Название компании.
- Географию работы.
- Услуги.
- Контактные данные.
- Реализованные проекты.
- Связь между услугами и проектами.

**2. First-hand Expertise**

Публиковать оригинальные сведения, основанные на реальном опыте компании:

- Как выполняются работы.
- Какие решения применяются.
- Какие сложности возникают.
- Как выбираются материалы.
- Как организуется взаимодействие.

**3. Structured Content**

Использовать:

- Понятные заголовки.
- Логичные разделы.
- Краткие определения.
- Списки этапов.
- FAQ.
- Таблицы сравнений, когда они действительно полезны.
- Содержательные подписи к изображениям.

**4. Verifiable Information**

Публиковать проверяемые факты:

- Реальные проекты.
- Подтверждённые характеристики.
- Реальные фотографии.
- Точные контакты.
- Фактическую географию работы.

**5. Source Authority**

Развивать присутствие компании на независимых и релевантных площадках:

- Профессиональные каталоги.
- Архитектурные платформы.
- Профильные публикации.
- Локальные бизнес-каталоги.
- Реальные партнёрские проекты.

Не покупать массовые упоминания и не создавать искусственные рекомендации.

### 11.3. FAQ Strategy

FAQ должен отвечать на вопросы реальных клиентов.

Примеры:

- Какие услуги предоставляет компания?
- В каких регионах Армении выполняются работы?
- Как рассчитывается стоимость строительства?
- Можно ли заказать ремонт квартиры?
- Какие этапы включает строительство частного дома?
- Можно ли обсуждать проект, проживая за границей?
- Какие материалы используются?
- Как проходит первоначальная консультация?

Ответы должны быть конкретными и отражать реальные условия компании.

### 11.4. GEO Technical Requirements

- Публичный HTML-контент доступен без обязательного выполнения JavaScript.
- Страницы имеют корректные HTTP-статусы.
- Важная информация представлена в текстовом виде.
- Используются понятные внутренние ссылки.
- Структурированные данные совпадают с видимым содержимым.
- Контент доступен для разрешённых поисковых роботов.
- Нет блокировки важных ресурсов на уровне Cloudflare или robots.txt.

Не требуется создавать специальные AI-файлы или использовать искусственные GEO-хитрости. Не существует гарантированного способа попасть в ответы AI-систем.

## 12. Technical SEO — Astro & Cloudflare

### 12.1. Rendering Strategy

Рекомендуется Astro SSG для публичных страниц.

Преимущества:

- HTML доступен при первоначальной загрузке.
- Меньше клиентского JavaScript.
- Предсказуемая генерация metadata.
- Хорошая совместимость с поисковыми роботами.

Интерактивные React Islands должны использоваться только там, где это необходимо.

### 12.2. Metadata Architecture

Создать централизованный SEO-компонент:

`src/components/seo/SEOHead.astro`

Ответственность:

- Title.
- Description.
- Canonical.
- Hreflang.
- Open Graph.
- Twitter Card.
- Robots.
- JSON-LD.

Данные получать из контентных коллекций и глобальных настроек.

### 12.3. Performance

Основные требования:

- Оптимизация Hero Image.
- Responsive Images.
- Font Optimization.
- Lazy Loading ниже первого экрана.
- Минимизация JavaScript.
- Code Splitting.
- Ограниченное использование GSAP.
- Отложенная загрузка тяжёлых видео.
- Стабильные размеры медиа.
- Кеширование статических ресурсов.

### 12.4. Cloudflare

Проверить:

- Корректную работу CDN.
- Отсутствие блокировки Googlebot и других разрешённых роботов.
- HTTP/HTTPS redirects.
- Единый canonical hostname.
- Корректное кеширование HTML и статических ресурсов.
- Отсутствие ошибочных challenge-страниц для поисковых роботов.
- Доступность sitemap и robots.txt.

### 12.5. HTTP Status Codes

- 200 — доступная страница.
- 301 — постоянное перенаправление.
- 404 — отсутствующая страница.
- 410 — окончательно удалённый ресурс, если это оправдано.
- 500 — серверная ошибка.

Не возвращать 200 для несуществующих страниц (Soft 404).

## 13. SEO Analytics & Monitoring

### 13.1. Google Search Console

Обязательная интеграция.

Отслеживать:

- Indexing.
- Performance.
- Search Queries.
- Page Performance.
- Core Web Vitals.
- Sitemap Status.
- Manual Actions.
- Security Issues.

### 13.2. Google Analytics 4

Рекомендуемые события:

- `page_view`
- `view_service`
- `view_project`
- `click_whatsapp`
- `click_telegram`
- `click_phone`
- `click_email`
- `form_start`
- `form_submit`
- `generate_lead`

`generate_lead` отправлять только после успешного сохранения заявки backend-системой.

### 13.3. Attribution

Для каждого лида сохранять:

- Landing Page.
- Referrer.
- UTM Source.
- UTM Medium.
- UTM Campaign.
- Locale.
- First Touch.
- Last Touch.

Эти данные должны согласовываться с системой Lead Attribution из SAD-001.

### 13.4. Monitoring Frequency

Рекомендуемый график:

**Weekly**

- Новые поисковые запросы.
- Органические переходы.
- Ошибки индексации.
- Новые лиды.

**Monthly**

- Анализ страниц услуг.
- Анализ портфолио.
- Эффективность языковых версий.
- Конверсии.
- Контентные пробелы.

**Quarterly**

- Пересмотр keyword mapping.
- Анализ конкурентов.
- Пересмотр контентной стратегии.
- Технический SEO-аудит.
